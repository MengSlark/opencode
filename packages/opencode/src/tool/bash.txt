在持久化 shell 会话中执行给定的 bash 命令，支持超时与安全处理。

默认所有命令在 ${directory} 下执行。若需在其他目录执行，请使用 workdir 参数。避免使用 `cd <目录> && <命令>`，改用 workdir。

重要：本工具用于终端操作（如 git、npm、docker 等）。不要用于文件操作（读、写、编辑、搜索、查找文件）——请使用对应的专用工具。

执行前请按以下步骤：

1. 目录确认：
   - 若命令会创建新目录或文件，先用 ls 确认父目录存在且正确
   - 例如执行 "mkdir foo/bar" 前，先用 ls foo 确认 foo 存在且为目标父目录

2. 命令执行：
   - 路径含空格时请用双引号（如 rm "带空格的路径/file.txt"）
   - 正确示例：mkdir "/Users/name/My Documents"、python "/path/with spaces/script.py"
   - 错误示例：mkdir /Users/name/My Documents、python /path/with spaces/script.py（会失败）
   - 确认引号正确后执行命令并捕获输出

用法说明：
  - command 参数必填
  - 可指定超时（毫秒）。未指定时默认 120000ms（2 分钟）
  - 用 5–10 个词简要描述该命令在做什么会很有帮助
  - 若输出超过 ${maxLines} 行或 ${maxBytes} 字节会被截断，完整输出会写入文件。可用 Read 的 offset/limit 读指定段落或用 Grep 搜索。因此无需在命令里用 head、tail 等做截断，直接执行即可

  - 除非用户明确要求或确实需要，避免用 Bash 执行 find、grep、cat、head、tail、sed、awk、echo。应优先使用专用工具：
    - 文件查找：用 Glob（不要用 find 或 ls）
    - 内容搜索：用 Grep（不要用 grep 或 rg）
    - 读文件：用 Read（不要用 cat/head/tail）
    - 编辑文件：用 Edit（不要用 sed/awk）
    - 写文件：用 Write（不要用 echo >/cat <<EOF）
    - 输出文字：直接输出（不要用 echo/printf）
  - 多条命令时：
    - 若相互独立可并行，在同一轮消息里发起多次 Bash 调用
    - 若存在依赖、必须顺序执行，用单次 Bash 调用并用 '&&' 串联（如 `git add . && git commit -m "message" && git push`）。例如 mkdir 后再 cp、先 Write 再 Bash 做 git、先 git add 再 git commit，都应顺序执行
    - 仅当需要顺序执行且不关心前一条是否失败时使用 ';'
    - 不要用换行分隔多条命令（引号内的换行可以）
  - 避免 `cd <目录> && <命令>`，用 workdir 参数指定工作目录
    <good-example>
    使用 workdir="/foo/bar" 与 command: pytest tests
    </good-example>
    <bad-example>
    cd /foo/bar && pytest tests
    </bad-example>

# 使用 git 提交变更

仅在用户明确要求时创建提交。若不明确，先询问。当用户要求新建 git 提交时，请严格按以下步骤：

Git 安全约定：
- 不要修改 git 配置
- 不要执行破坏性/不可逆的 git 命令（如 push --force、hard reset 等），除非用户明确要求
- 不要跳过钩子（--no-verify、--no-gpg-sign 等），除非用户明确要求
- 不要对 main/master 执行 force push，若用户要求应予以提醒
- 避免 git commit --amend。仅在以下全部满足时使用 --amend：
  (1) 用户明确要求 amend，或提交已成功但 pre-commit 钩子自动改动了需要包含的文件
  (2) HEAD 提交由你在本会话中创建（可用 git log -1 --format='%an %ae' 核对）
  (3) 提交尚未推送到远端（可用 git status 确认 "Your branch is ahead"）
- 若提交失败或被钩子拒绝，绝不要用 amend，应修复后新建提交
- 若已推送到远端，除非用户明确要求（并需 force push），否则绝不要 amend
- 仅在用户明确要求提交时才提交，否则用户会感到过于主动

1. 可在单次回复中发起多次工具调用。当需要多种独立信息且命令都可能成功时，为求性能可并行执行以下 Bash 调用：
   - 执行 git status 查看未跟踪文件
   - 执行 git diff 查看将提交的已暂存与未暂存变更
   - 执行 git log 查看近期提交信息以符合仓库的提交风格
2. 分析所有将提交的变更（含此前已暂存与新加入的），起草提交信息：
   - 概括变更性质（如新功能、功能增强、修复、重构、测试、文档等），确保信息准确反映变更与目的（如 "add" 表示全新功能，"update" 表示对现有功能的增强，"fix" 表示修复）
   - 不要提交可能含敏感信息的文件（.env、credentials.json 等）。若用户明确要求提交此类文件应予以提醒
   - 起草简洁（1–2 句）的提交信息，侧重「为什么」而非「做了什么」
   - 确保准确反映变更与目的
3. 当需要多种独立信息且命令都可能成功时，可并行执行：
   - 将相关未跟踪文件加入暂存区
   - 用上述信息创建提交
   - 提交完成后执行 git status 确认成功
   注意：git status 依赖提交完成，故应在提交之后顺序执行
4. 若因 pre-commit 钩子导致提交失败，修复问题后新建提交（参见上述 amend 规则）

重要说明：
- 除 git 相关 bash 命令外，不要额外执行读代码或探索代码的命令
- 不要使用 TodoWrite 或 Task 工具
- 除非用户明确要求，否则不要推送到远端
- 不要使用带 -i 的 git 命令（如 git rebase -i、git add -i），因其需要交互输入且不被支持
- 若无变更可提交（无未跟踪文件且无修改），不要创建空提交

# 创建 Pull Request

所有与 GitHub 相关的操作（issue、pull request、检查、发布等）均通过 Bash 工具执行 gh 命令。若给出 GitHub URL，用 gh 获取所需信息。

重要：当用户要求创建 pull request 时，请严格按以下步骤：

1. 当需要多种独立信息且命令都可能成功时，可并行执行以下 Bash 调用，以了解当前分支自与主分支分叉后的状态：
   - 执行 git status 查看未跟踪文件
   - 执行 git diff 查看将提交的已暂存与未暂存变更
   - 检查当前分支是否跟踪远端分支以及与远端是否一致，以判断是否需要 push
   - 执行 git log 与 `git diff [base-branch]...HEAD` 了解当前分支的完整提交历史（自与基准分支分叉起）
2. 分析将包含在 PR 中的所有变更，确保查看所有相关提交（不仅是最近一次，而是将包含在 PR 中的全部提交），并起草 PR 摘要
3. 当需要多种独立信息且命令都可能成功时，可并行执行：
   - 如需则创建新分支
   - 如需则用 -u 推送到远端
   - 使用 gh pr create，按以下格式创建 PR。使用 HEREDOC 传入 body 以保证格式正确
<example>
gh pr create --title "PR 标题" --body "$(cat <<'EOF'
## Summary
<1-3 条要点>
EOF
)"
</example>

注意：
- 不要使用 TodoWrite 或 Task 工具
- 完成后返回 PR 的 URL 供用户查看
